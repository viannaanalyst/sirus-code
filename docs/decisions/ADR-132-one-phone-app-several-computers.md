# ADR-132: One phone app, several computers

**Status:** Accepted (2026-10-13); the archiving it describes is superseded by [ADR-173](ADR-173-conversation-archive-removed.md).

## Context

The owner runs two Sirus servers on one tailnet: the Mac app's remote server (ADR-080, ADR-082) and the headless `sirus-host` on a VPS (ADR-131). Each served its own phone app from its own origin with its own pairing, so the phone had two home-screen apps, two inboxes, and nothing when the computer an app came from was off. He wants one phone app that shows the conversations of both together and keeps working with either one offline.

## Decision

- **Environments on the phone.** `lib/environments.ts` keeps a list of computers in local storage (`sirus.environments`): `{ id, label, kind: "mac" | "server", baseUrl, token, hostName }`. The origin the app was installed from is the `home` computer; its token stays under the old `REMOTE_TOKEN_KEY`, so existing pairings keep working and never appear in the list. Other computers are added in Settings → Connections → Add computer with the address (`name.tailnet.ts.net`, normalized to an `https://` origin) and the six-digit code; the phone posts to `{baseUrl}/api/pair` cross-origin and stores the token it gets. Each computer has a row with its status (in use, online, offline, connecting, pair again), a name the person can change, Use this computer, and Forget on this phone (the token is dropped locally; revoking it on the computer stays a Connections action there).
- **One active computer, the store unchanged.** `client` keeps its shape: in the phone's build it sits on a `SwitchingTransport` that forwards calls to the active computer's `RemoteTransport` and moves every listener when the active computer changes. Each computer has its own `RemoteTransport` (socket URL and thumbnail/device-hub URLs from its `baseUrl`). Switching (`useEnvironments.activate`) snapshots the store's conversations as that computer's summary, moves the transport, then runs the usual `bootstrap()`; `bindRealtime` needs no rebinding. The chosen computer is remembered (`sirus.environments.active`); a computer that cannot be reached when the app opens gives way once to one that can.
- **Summaries for the merged Home.** Every other paired computer is watched through its own `SirusClient`: `load_state` and `host_info` on each (re)connection, then `session-updated` and `settings-changed` keep a trimmed summary (no transcripts, side chats left out, at most 150 recent conversations, its archived and pinned ids). Summaries are cached in `sirus.environments.summaries` so an offline computer's last-known conversations still show, dimmed with an offline marker; opening one is refused with a toast. The active computer's own data is cached the same way (debounced), so it also shows when it is the one that is off.
- **Phone UI.** Home merges every computer through `mergeEnvironments` and the usual `homeSections` (the active computer wins a duplicate id); with more than one computer each row shows a small marker (laptop or server icon and the computer's name) before its time, kept to one line. Rows of other computers have the same swipe and menu, run on their own computer (see the addendum); tapping one switches computers, then opens the conversation. Choose project and Projects group projects under each computer's name, the active one first; picking a project on another computer switches first. An alert for a conversation on another computer switches before opening it. Messages written offline go out only to the computer their conversation is on.
- **Server side (`remote.rs`, shared by the Mac app and the host).** The guard still lets only loopback and Tailscale peers in, and a same-origin page through as before. A cross-origin request is allowed only when its `Origin` is `https://<name>.ts.net` (no port, path or user) on this computer's tailnet (the suffix of its own HTTPS name, from `tailscale serve` or the host's `--url`; any `*.ts.net` when unknown), and then only for `/api/pair` and `/api/health`, or for any route when that origin was recorded with a paired device. Pairing from another computer's page records that origin on the device (`origins` in `remote.json`); revoking the device removes it. Allowed cross-origin requests get CORS answers (preflight for `GET, POST, PUT, DELETE` with `authorization, content-type`, `Access-Control-Allow-Origin` echoing the origin, `Vary: origin`, no credentials). The WebSocket additionally binds the token to the origin: a socket opened from another page must carry the token of the device that paired from that page. Device tokens stay mandatory on every API route and the socket. The phone page's CSP allows `connect-src https://*.ts.net wss://*.ts.net`.
- **Identity.** `/api/health` and the pairing reply return `{ id, hostName, kind }`: a stable random host id kept in `remote.json`, the machine name and `mac` (desktop build) or `server` (host build). The phone names a Mac "Mac" and a server by its host name unless the person renames it.

## Push alerts

Each computer signs web push with its own VAPID key (ADR-082), and a service worker registration holds one push subscription bound to one `applicationServerKey`; subscribing again with another key fails until the first is dropped. So alerts keep coming only from the home computer, unchanged, and Settings → Alerts says so when several computers are known. Possible fixes: let the owner's computers share one VAPID key (copied from the home computer to the other at pairing, over the authenticated channel), so both can post to the same subscription; or let one computer relay the other's alerts.

## Consequences

- A phone with one computer behaves as before: same storage key, same transport, same screens.
- Both computers must run this version (CSP and CORS) for the phone to reach the second one; nothing needs re-pairing at home. Adding a second computer is a new pairing from Settings → Connections.
- Switching computers reloads the store; the conversation's transcript and Git state load from the new computer. Per-computer caches (Git identities, pull requests, browser state) are rebuilt by `bootstrap`.
- Anything on a page served by any `*.ts.net` name on the tailnet can try pairing, as any tailnet peer already could; the code is still required, and only recorded origins reach the API.

## Addendum (2026-10-13): actions on every computer's rows

Rows of other computers are no longer read only. They get the same swipe actions and long-press menu as the active computer's (`MobileSessionItem` with an `environmentId`), and each action runs on the computer the conversation lives on, through that computer's background client, without switching: `useEnvironments.sessionAction` calls the same native commands the store uses (`save_settings` for archive, unarchive, pin and unpin; `snooze_session`, `rename_session`, `set_session_auto_archive`, `delete_session`; `worktree_cleanup_action` after archiving when that computer releases worktrees on archive). Archive and pin lists are per computer: the change is applied to that computer's own settings (kept in memory from `load_state` and `settings-changed` while it is watched, loaded fresh otherwise), never to the active computer's. Its summary is updated from the reply and then reloaded. No action needs a switch. `rowActionRoute` decides per row (store, that computer's client, or unreachable); while the computer is offline or still connecting the row stays dimmed, the swipe buttons are disabled and the menu says "<Computer> is offline" (or "Connecting to <Computer>…") with only Copy conversation ID and Arrange (a phone preference) still available. The undo toast after snoozing stays an active-computer feature.

## Addendum (2026-10-14): offline computers

- **Rows look normal.** A computer out of reach no longer dims its conversations or turns its marker orange. Instead Home opens with one quiet line per such computer, "Reconnecting to <Computer>…", with a wifi-off icon (a spinner while it is trying), from `unreachableEnvironments` (`EnvironmentStatus`).
- **Actions wait on the phone.** Archive, restore, snooze, return, pin, rename, auto-archive and delete on a row whose computer cannot be reached (another computer, or the active one while its connection is lost) are queued like the message outbox (`phone-outbox.ts`): `queueRowAction` keeps them in `sirus.environments.pending` (at most 100; a later change of the same kind to the same conversation replaces the earlier one, a delete replaces everything waiting for it). The menu says "Applies when <Computer> is back"; Copy conversation ID still works at once. Rows show a small clock until the action is applied, and the merged lists already show the result (`summaryWithPending`: archived, pinned, snoozed, renamed or gone). When that computer's connection opens, `flushPendingActions` sends its actions in order (through that computer's client, or the store's own actions when it is the active one); one that fails stays with the rest behind it.
- **Archived and Snoozed show every computer.** Both pages read the merged data (`useMergedHome`) with a computer filter at the top (All, then one chip per paired computer; `filterByEnvironment`), the computer marker on each row, and restore or return routed to the conversation's computer (or queued for it). Home's counts link to them across computers.
- **Undo after snoozing on any computer.** Snoozing a row of another computer (or a queued one) raises the same toast; its Undo returns the conversation on that computer (`snoozeNotice.undo`).

## Addendum (2026-10-14): alerts from the other computers

Push alerts used to come only from the computer the phone app was installed from, because a web-push subscription is tied to one VAPID key (the Mac's). Now the other computers alert the same app with that key:

- **The key moves between the owner's computers only.** The desktop, once a paired computer answers, calls `share_push_identity(baseUrl, token)`. The Mac's Rust side reads its key and `PUT`s it to that computer's `/api/push/identity` over the tailnet (HTTPS `*.ts.net` only, with the desktop's device token). The key never reaches a page. `share_push_identity` is on the remote denylist, so a phone cannot ask for it. The receiving computer validates a 32-byte P-256 key, stores it as its VAPID key and marks it adopted (`vapid_adopted`). A computer with an adopted key never passes it on.
- **The phone registers its subscription.** Its existing subscription (the one made with the Mac's key) goes to every other paired computer with that computer's device token: `PUT /api/push`, cross-origin as ADR-132 allows. This happens when the computer connects (once per launch) and when alerts are turned on; turning alerts off removes it there too.
- **The Mac owns the app icon's count.** With an adopted key, a computer's alerts carry no badge.

Consequence: a computer that adopts the key loses its own key, so a phone app installed from that computer's page would stop getting its alerts. The owner's phone app is installed from the Mac.
