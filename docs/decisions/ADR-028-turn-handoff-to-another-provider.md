# ADR-028: Turn-level handoff to another provider

**Status:** Accepted

## Context

The assistant-response action used to fork (ADR-016): it copied the transcript
through a settled response into a new session with its own isolated worktree,
preserving the source provider. The product direction is Monocode's handoff:
pick another agent on a finished response and continue the work there, sharing
the workspace, without cloning the raw transcript.

## Decision

- `handoff_session(session_id, message_id, agent, model)` creates a new idle
  session in the source's project and **same worktree/branch** (no Git
  mutation, uncommitted work continues), with the target provider/model and
  that provider's selected account. The transcript is empty; `handoff:
  { from, brief, request, pending }` carries a deterministic, bounded recap
  built through the chosen response (last two user messages at 240 chars, the
  last assistant response at 500, 1,800 total) plus a 240-char request preview.
- The first send wraps the computed process prompt with the Monocode-style
  preamble (`You are continuing an existing conversation handed off from …`)
  and a `<handoff>` block, then consumes `pending` once. The persisted user
  message keeps only the visible text, so the composer transcript stays clean.
- `dismiss_handoff(session_id)` drops the pending recap; the source session is
  untouched.
- The assistant action is a provider→model picker with only installed and
  enabled providers other than the current one. Until first send, the composer
  shows a dismissible card (from → to provider and the request preview).
- The source session must be stopped, exactly like a fork boundary. The native
  `fork_session` command remains for existing `forkOrigin` sessions and their
  banner; the UI entry point is now the handoff.

## Consequences

- **Positive:** switching agents keeps the working tree exactly as the previous
  agent left it; the new provider receives a focused recap instead of a raw
  transcript, and vendor state stays clean because no native thread is copied.
- **Negative:** two sessions can point at the same worktree (source must be
  stopped; deleting the source with "remove worktree" can strand the handoff
  session). The recap is lossy by design.
- **Accepted trade-off:** no automatic send — the card waits for an explicit
  Send, matching the existing composer contract.

## Alternatives considered

- Keep the Synara-style fork (transcript copy + new isolated worktree):
  rejected by the product owner; it loses uncommitted work and carries raw
  history instead of a recap.
- Same-session provider switch with a recap generated by the outgoing agent
  (Monocode's composer switch): requires a live outgoing turn and adds a
  timeout/approval dance; the turn action targets an already-settled boundary.
- Copying the transcript and also sending a recap: duplicates context and
  doubles the prompt budget.
