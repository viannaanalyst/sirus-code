# ADR-142: Scheduled tasks

- Status: accepted. Superseded by ADR-172 (Tasks and scheduled tasks removed).
- Date: 2026-10-18

## Context

The owner saw scheduled prompts in another coding-agent app and asked for them in Sirus Code: "check the CI every morning", "summarize yesterday's pull requests on Mondays", "remind this conversation in two hours to re-run the benchmark". The app once had a scheduler (`automations.rs`, ADR-051) that only Astros used; it was removed with them (ADR-116). What remains is the start path those runs used: `launch.rs` creates a visible session and admits its first turn through `send_prompt`.

## Decision

- **Model.** `scheduled_tasks.rs` keeps up to 50 `ScheduledTask`s in `AppData.scheduledTasks`, stored one row each in a new `state.db` table `scheduled_tasks` (schema version 5; not `automations`, which version 2 drops). A task is a title (1–200 printable characters), a prompt (1 byte to 64 KiB, no NUL; the first turn's text is exactly this prompt), a project, a provider and model, an approval mode, a schedule and `sessionId`:
  - `null`: every run starts a new conversation titled with the task, in its own isolated worktree, through `launch::launch`;
  - a session of the same project: every run continues that conversation through `send_prompt`, the Send button's admission.
  Run state rides along: `nextRunAt`, `lastRunAt`, `lastStatus` (`never`, `running`, `succeeded`, `failed`, `missed`), `lastError`, `lastSessionId`, `runCount`, and a stored failure streak the renderer never sees. `createdBy` is `person` or `agent` and an edit never changes it.
- **Schedules,** in local time (chrono `Local`): `once { at }` (Unix ms), `daily { time: "HH:MM" }`, `weekly { days, time }` (0 = Sunday … 6, at least one, kept sorted without repeats) and `interval { minutes }` (15 to 10,080). A local time that does not exist on a DST change resolves to the next valid instant and a repeated one to its first occurrence, as the old engine did. Saving a task computes `nextRunAt` only when it is new or its schedule or `enabled` changed, so a rename keeps the next run and all run state. A `once` in the past is refused ("Pick a time in the future.") when it is new, rescheduled or turned back on.
- **Timer.** One tokio task, started at app start on the Mac and the headless host, sleeps until the earliest `nextRunAt` but never more than 60 seconds (the monotonic sleep stops while the Mac sleeps), and any change wakes it through a `Notify`. A due task moves to its next occurrence before it starts, so nothing fires twice; a `once` turns itself off and keeps its row.
- **Missed runs.** A run more than 10 minutes late (app closed, Mac asleep) is recorded `missed` and the task moves to its next occurrence; a late `once` is marked missed and turned off. An `interval` runs once when overdue and reschedules from that run. Never a burst.
- **Runs.** `succeeded` means the turn was admitted (as in T3 Code); a failed launch or send records `failed` with one short `lastError`. Three failed runs in a row pause the task (`enabled` false, "Paused after 3 failed runs: …"); turning it back on resets the streak. A run is skipped, not queued, while the previous run's conversation is still starting, running or waiting. A bound conversation that is busy is retried every minute for up to 30 minutes, then the run fails with "The conversation was busy."; one that was deleted fails at once with "The conversation no longer exists." and the task stays. Run now runs at once even when the task is off and leaves `nextRunAt` alone; where a scheduled run would skip or wait it answers with an error instead. A run cut by a quit before its turn was admitted reads as failed at the next launch. Removing a project removes its tasks.
- **Safety.** The provider must be enabled and the model pass `launch::valid_model`. The approval mode is stepped down to what the provider offers, never up (`execution::approval_for`, as delegation does), at save and again at every run against the conversation's own provider. Runs are normal sessions: sidebar, notifications, Stop.
- **Contract.** One closed command `scheduled_task_action { list | upsert | delete | setEnabled | runNow }` (`deny_unknown_fields`) answers `{ tasks }`, and `scheduled-tasks-changed` carries the same snapshot on every change and on every run start and finish. `load_state` leaves scheduled tasks out. Like `task_action`, paired devices and the headless host may call it (not in `remote.rs`'s denied list); the host's generated command table picks it up from `lib.rs`.
- **Agent tools.** Behind "Let agents manage sessions" with the other `sirus_*` tools (listed only with the child flag, rechecked per call, refused in planning and pull-request Ask conversations):
  - `sirus_schedule_task { title?, prompt, schedule, bindToThisConversation? (default true), project?, model?, enabled? }`: the schedule has the stored shape and `once.at` may be ISO 8601 (local when it has no offset). The task takes the caller's provider and model and the caller's own approval mode, never broader; `createdBy` is `agent`. A bound task must stay in the caller's project. It answers the task with its schedule label and `nextRunAt` in ISO 8601.
  - `sirus_list_scheduled_tasks { project? }`.
  - `sirus_update_scheduled_task { id, title?, prompt?, schedule?, enabled? }`, `sirus_delete_scheduled_task { id }` and `sirus_run_scheduled_task_now { id }` refuse a task whose approval is broader than the caller's, so an agent cannot raise its own access through a task.

## Scheduled tasks UI

The owner chose to keep them in plain sight (unlike the reference app, where they sit in Settings) and to leave the composer alone:

- **Tasks → Scheduled.** The Tasks page has two tabs, "To do" and "Scheduled", with counts; on Scheduled the header offers New task. Each row shows the title, the prompt (two lines), chips for when it runs and the next run ("Every day at 02:00 · next in 4h", or "paused"), the project, the provider and model, the bound conversation and the last result (started, failed, missed, running now; failed shows its error), an on/off switch and a menu with Run now, Edit, Open last conversation and Delete (confirmed). Enabled tasks come first by next run; paused ones are dimmed. Agent-created tasks carry a "created by an agent" chip. Rows rise in once; none with reduced motion.
- **Editor** (dialog): name, prompt, project, provider and model, When (Once with date and time, Every day, On days with weekday toggles, Every N minutes/hours/days, 15 minutes to 7 days), Where it runs (a new conversation in its own worktree each time, or always the same conversation of that project), permissions (the provider's approval modes, Ask by default, with what each means for an unattended run), and a live "Next run: … · then …" preview computed by `lib/scheduled-tasks.ts` with the native timer's rules. Save, or Save and run now.
- **No clock in the composer.** A conversation asks its agent instead ("run this every day at 9"): the `sirus_schedule_task` tool binds the task to that conversation by default. While an enabled task continues a conversation, a quiet line above its composer says when ("Every day at 02:00 · Nightly review · See"), opening Tasks → Scheduled.
- State lives in `store/scheduled-tasks-store.ts`, mirrored from `scheduled_task_action` and the `scheduled-tasks-changed` event; labels and the form are pure helpers with tests.
