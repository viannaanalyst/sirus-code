# ADR-140: In-app updates and the release command

- Status: accepted
- Date: 2026-10-18

## Context

Sirus Code is published as GitHub releases of `viannaanalyst/sirus-code` (v0.1.0 shipped `SirusCode-arm64.dmg`, built by hand). There was no way for an installed app to learn about or install a newer version, and every release was a sequence of manual steps. The app is not notarized yet (no Apple Developer account), so a downloaded DMG needs Privacy & Security → Open Anyway the first time.

## Decision

- **Updater from Rust only.** `tauri-plugin-updater` is registered in the desktop build (`#[cfg(feature = "desktop")]`, listed in `build.rs`'s desktop-only modules so the headless host neither links nor generates it). The renderer gets no updater or process permission in `capabilities/default.json`; it reaches `app_update.rs` through one closed command, `app_update_action { status | check | install | restart }`, and the `app-update` event (`AppUpdateStatus`: current version, phase, offered version, notes, date, download progress, error, last check). The command is in `remote.rs`'s denied list and in `lib/computers.ts`'s this-Mac commands, so a paired device or another computer's window never updates this Mac.
- **Feed.** The endpoint is `https://github.com/viannaanalyst/sirus-code/releases/latest/download/latest.json` (a static feed: version, notes, `pub_date`, `platforms.darwin-aarch64` with the `.app.tar.gz` URL and its signature). The plugin rejects anything not signed by the minisign public key in `tauri.conf.json` → `plugins.updater.pubkey`.
- **When it checks.** Release builds check 20 seconds after launch and again when the main window gains focus, at most every 4 hours; there is no polling timer. Automatic checks fail silently (offline, no feed yet). Development builds (`tauri dev`, the owner's `build:desktop` app) never check on their own; Settings can still check.
- **Installing needs two explicit steps and the close guard.** The toast "Sirus Code {version} is available · Update / Later" (top-center stack, same entrance and exit as the other toasts) and Settings → Advanced → About → Updates ("Check for updates", then Update, then Restart) are the only ways in. Update downloads, verifies and installs the bundle in place, then restarts through the same `CloseGuard` as quitting (ADR-090): with agents running and "confirm before closing" on, a native "Restart to update?" dialog asks first; declining keeps working, and the new version starts at the next launch or from Restart. The restart uses `AppHandle::request_restart`, which runs the normal shutdown (state saved, agents stopped) before relaunching. Later hides that version's offer for this launch.
- **Signing key outside the repository.** The private key is `~/.config/sirus-code/updater.key` (mode 600, folder 700) with no password: the release runs unattended on the owner's Mac, and a password stored next to the key would add no protection; the Mac's disk encryption and account protect it. `.gitignore` ignores `*.key`, `*.key.pub`, `*.pem` and `updater.key*` anywhere. Losing the key means installed apps can no longer accept updates (they would need a manual reinstall with a new public key), so it must be backed up, for example in a password manager.
- **`npm run release -- <version>`** (`scripts/release.ts`, pure parts in `scripts/release-lib.ts`): checks main, a clean tree, an up-to-date `origin/main`, `gh` signed in and that the version is newer than package.json and the last tag; bumps package.json, tauri.conf.json, Cargo.toml and Cargo.lock; runs typecheck, lint, tests, both clippy builds and cargo test unless `--skip-checks`; builds the release `.app` and DMG (`tauri build --bundles app,dmg` with `createUpdaterArtifacts` and the DMG window from tauri.conf.json) signed with "Sirus Code Local Signing" when that identity exists (ad-hoc otherwise; a stable identity keeps macOS privacy grants across updates), signs the update with `TAURI_SIGNING_PRIVATE_KEY`, verifies that signature against the configured public key, writes `latest.json` (notes from `--notes` or the commit subjects since the last tag), commits "Release vX.Y.Z", tags, pushes and runs `gh release create` with `SirusCode-arm64.dmg`, `SirusCode-arm64.app.tar.gz`, its `.sig` and `latest.json`. `--dry-run` builds and writes the same files under `src-tauri/target/release-upload/vX.Y.Z/` (the version passed to the build instead of edited files) and only prints the git and GitHub commands. A failure before the commit restores the version files.
- **Notarization is optional.** With `APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID` (or `APPLE_API_KEY`/`APPLE_API_ISSUER`/`APPLE_API_KEY_PATH`) and a Developer ID identity in `APPLE_SIGNING_IDENTITY`, the build notarizes; otherwise those variables are removed from the build and the script says notarization was skipped.

## Amendment: header pill, background download and What's new

The owner chose a pill in the window header over the toast, and asked for updates that download on their own and say what changed.

- **The header pill** (`AppUpdatePill`, desktop only) replaces the toast. It shows "Update 0.2.0" with a soft pulsing dot when a version is on offer, a progress ring with the percentage while it downloads, "Installing…", then "Restart to update" in green; a failed install turns it red. Clicking opens a panel with the version, the date, its notes read into sections (`lib/release-notes.ts`: `#` headings start sections, `-`/`*` lines are items; plain text only), the download progress in MB, and one action: Download and install, Try again, or Restart now / When I quit.
- **Background download.** New settings, all on by default and validated natively: `appUpdateAutoCheck` (release builds check on their own), `appUpdateAutoDownload` (a version found on its own is downloaded, verified and installed right away, then waits) and `appUpdateWhatsNew`. The closed command gains `download`: the same download and install as `install`, without the restart. Nothing ever restarts on its own; Restart still goes through the close guard, and an installed update also starts at the next launch.
- **What's new.** When an update is installed, its notes are kept in `appUpdateNotes` (version, notes up to 4,000 characters, date, `seen`). The first launch of that version shows them once in a dialog with a coloured band and the version tag; Continue marks them seen. Settings → Advanced → About shows the update control, the three switches and "What's new" to open the notes again; the old "Check for updates automatically · Coming soon" row in General is gone.
- **Release notes** should be written for people: `npm run release -- 0.2.0 --notes "## New\n- …\n## Fixes\n- …"`; without `--notes` they fall back to the commit subjects.

## Consequences

- Installed apps from the first release built this way (v0.1.1 on) update themselves when the owner publishes; v0.1.0 has no updater and must be replaced by hand once.
- Only Apple silicon Macs are published (`darwin-aarch64`); an Intel or universal build would add a platform to `latest.json`.
- Updates replace the app bundle in place: an app installed where the user cannot write needs the system's permission prompt.
- Without notarization a downloaded DMG still needs Open Anyway the first time; updates installed by the app do not, since they are not quarantined.
